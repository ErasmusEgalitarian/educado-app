# Contributing to educado-app

Thanks for your interest in contributing. Educado is an educational platform for
waste pickers in Brazil, built as a partnership between the University of
Brasilia (UnB) and Aalborg University. This repository holds the Android mobile
app, built with Expo and React Native.

By participating in this project you agree to follow our
[Code of Conduct](CODE_OF_CONDUCT.md).

## Prerequisites

- **Node.js 20 or newer** and npm.
- **Java 17.** `.sdkmanrc` pins `17.0.16-tem` if you use SDKMAN.
- **Android SDK.** Android Studio, or the standalone Command Line Tools. You
  need build-tools, platforms 35 and 36, and NDK 27, plus either a physical
  device with USB debugging enabled or an emulator AVD.
- Optional but recommended: **Nix.** `flake.nix` provisions the whole Android
  toolchain (build-tools, platforms, NDK, cmake, emulator, system images). Run
  `nix develop` to enter the devshell with everything configured.
- Optional, for cloud builds: the **EAS CLI** (`>= 16.28.0`, see `eas.json`) and
  access to the Expo project.

The app targets **Android**. There is an `npm run ios` script, but no iOS build
profile is configured and iOS is not tested.

## Local setup

```bash
git clone https://github.com/ErasmusEgalitarian/educado-app.git
cd educado-app
npm install
cp .env.example .env
```

Then set `EXPO_PUBLIC_API_URL` in `.env`. It is the only environment variable and
it is required: `utils/api-config.ts` throws at boot when it is missing.

| Target | Value |
| ------ | ----- |
| Production API | `https://api-educado.tominho.com` |
| Local API, Android emulator | `http://10.0.2.2:5001` |
| Local API, physical device on the same LAN | `http://192.168.x.y:5001` |

Notes:

- `10.0.2.2` is how the Android emulator reaches the host machine's
  `localhost`. Plain `localhost` inside the emulator points at the emulator
  itself.
- Cleartext HTTP is allowed only for development hosts, through the
  `plugins/withAndroidSecurity.js` config plugin. Any production API must be
  HTTPS.
- The old auto generated Coolify hostname
  `https://igg084s4s08sk0w08gsc0cgk.tominho.com` is dead and answers 503. Do not
  copy it from an old `.env` or an old build.
- Never commit `.env`, the keystore in `credentials/`, or any token. They are
  gitignored for a reason.

## Running the app

```bash
npm run start     # Metro dev server (expo start)
npm run android   # native build and install on device or emulator
npm run web       # expo start --web, partial support
```

The native folders `/android` and `/ios` are generated by prebuild and are not
versioned. If you change `app.config.ts` or anything under `plugins/`, you need
a native rebuild (`npm run android`), a Metro reload is not enough.

## Branching and pull requests

The default branch of this repository is `main`. There is also a long lived
`dev` branch used to integrate work before it reaches `main`.

1. Create your branch from `dev` unless a maintainer tells you otherwise.
2. Name it with a type prefix and a short kebab-case description, following the
   branches already in the repository:
   - `feat/student-phone-auth`
   - `fix/video-network-ux`
   - `refactor/native-bottom-sheet`
   - `docs/github-templates`
3. Keep the branch focused. One concern per pull request.
4. Rebase or merge the target branch into yours before asking for review, so the
   diff stays clean.
5. Open the pull request against `dev` (or `main` for a release or a hotfix,
   when a maintainer asks for it) and fill in the pull request template.
6. Pull requests need at least one approving review. Do not merge your own pull
   request without one.
7. The quality gate below must pass before review.
8. For anything with a visible UI change, attach a screenshot or a screen
   recording from an Android device or emulator.

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```
<type>(<optional scope>): <short imperative description>

<optional body>

<optional footer, e.g. Closes #123>
```

Types in use in this repository: `feat`, `fix`, `chore`, `docs`, `refactor`,
`test`, `build`, `perf`, `ci`, `style`.

Examples taken from the project history:

```
feat(auth): login do aluno por telefone (remover email do cadastro)
fix(video): UX de rede ruim/queda nos players de aula
fix(deps): alinhar dependencias ao Expo SDK 56
chore: ignorar CLAUDE.md (doc local de dev, fora do repo)
```

Guidelines:

- Subject line in the imperative mood, no trailing period, ideally under 72
  characters.
- Use the scope to name the affected area (`auth`, `video`, `activities`,
  `i18n`, `downloads`, `deps`).
- A breaking change is marked with `!` after the type or scope
  (`feat(auth)!: ...`) and explained in the body.
- Commit subjects in this repository are written in Portuguese or English. Match
  the surrounding history, do not mix both in one subject.

## Quality gate: lint and typecheck

There is no automated test suite in this repository. Run both checks below
before pushing. This is the same checklist maintainers run on review:

```bash
npm run lint       # ESLint 9 flat config (expo + google base + prettier)
npx tsc --noEmit   # TypeScript strict type check, no emit
```

Auto-fix formatting instead of hand-formatting:

```bash
npm run lint:fix
```

A pull request with lint errors or type errors will not be reviewed.

## Internationalization is mandatory

The app ships in Portuguese (`pt-BR`, default and fallback locale) and English
(`en`). **No user facing string may be hardcoded.**

- Import the helper: `import { t } from '@/i18n/config'`.
- Render text through `t('section.key')`, never as a literal.
- Add every new key to **both** `locales/pt-BR.json` and `locales/en.json`. The
  two files must stay in parity: a key present in only one of them is a bug.
- Keep the nesting shape consistent with the existing groups (`common`,
  `landing`, and so on) instead of inventing a flat key.
- The selected language is persisted in AsyncStorage under `@educado:language`
  and changing it remounts the navigation stack. If your screen caches strings
  in state, make sure it re-renders on a language change.

A pull request that adds a literal string to the UI will be sent back.

## Code standards

- **TypeScript strict mode.** Do not introduce `any` to silence the compiler.
  If a type is genuinely unknown, use `unknown` and narrow it.
- **Path alias.** `tsconfig.json` maps `@/*` to the project root. Use
  `@/services/api`, `@/contexts/AuthContext`, not long relative paths.
- **Layering.** Keep the existing separation:
  - `app/` holds expo-router routes only. Screens compose components, they do
    not implement business logic.
  - `components/` is UI grouped by domain.
  - `services/api.ts` owns every HTTP call. Components must never call it
    directly.
  - `hooks/` wraps `services/api.ts` with react-query and maps the backend
    `Api*` types to the domain types in `data/mock-data.ts`.
  - `utils/` holds pure helpers with no React dependency.
- **Formatting.** No semicolons, single quotes, Prettier through
  `eslint-plugin-prettier`. Run `npm run lint:fix`.
- **Storage.** The JWT goes in `expo-secure-store`. Everything else goes in
  AsyncStorage under an `@educado:` prefixed key.
- **Offline support is a feature, not an afterthought.** The audience often has
  no connectivity. If you touch course content, media loading or progress, check
  the offline path in `services/download-manager.ts`,
  `utils/progress-storage.ts` and `utils/progress-sync.ts` and keep it working.
- **New Architecture.** `newArchEnabled: true` in `app.config.ts` is required by
  reanimated v4 and worklets. Do not turn it off.
- **Dependencies.** Adding a dependency is a design decision. Open an issue or
  explain it in the pull request description: why it is needed, what
  alternatives you considered, and whether it is compatible with Expo SDK 56 and
  the New Architecture. Prefer an `expo-*` package when one exists, and install
  with `npx expo install` so the version matches the SDK.

## Builds with EAS

Android profiles live in `eas.json`: `development` (dev client),
`preview` (internal app-bundle), `preview-apk` (internal apk) and `production`.

```bash
npm run eas:preview          # cloud build
npm run eas:preview-local    # local build, loads .env through dotenv-cli
npm run eas:production
npm run eas:submit           # Play Store submission
```

`EXPO_PUBLIC_API_URL` is inlined into the bundle at build time, so a build
carries whatever value was set when it was produced. Check the EAS environment
before producing a release build:

```bash
eas env:list
```

## Reporting bugs and requesting features

Open an issue using the bug report or feature request template in
`.github/ISSUE_TEMPLATE/`. Search existing issues first to avoid duplicates. For
a bug, always include the device model, the Android version, the app version and
the Expo SDK version.

## Security issues

Do not open a public issue for a security vulnerability. Follow
[SECURITY.md](SECURITY.md) and report it privately to 190091681@aluno.unb.br.
